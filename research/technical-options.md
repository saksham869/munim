# Technical options considered

| Decision | Options considered | Chosen | Why |
|---|---|---|---|
| Who decides whether money is spent | An LLM judging each offer; an ML classifier trained on past campaigns; deterministic rules | Deterministic rules in integer paise (`munim/policy.py`) | A spend decision must be repeatable, explainable line by line, and impossible to talk around. There is no labelled campaign history to train a classifier on. A model judge can be prompt-injected by the very agent it is supervising |
| How results are measured | Frequentist A/B test; Bayesian Beta-binomial with a pooled prior; uplift modelling | Beta-binomial with a prior on the held-back group's return rate pooled across shops, Monte Carlo for the chance of profit (`munim/measurement.py`) | Campaigns have 20 to 60 customers, too few for significance tests or uplift models. A probability of profit is what an owner can act on. Simulated comparison and its failure mode are in `evaluation/metrics.md` |
| Who gets held back | Random draw per run; the agent chooses; keyed hash | HMAC-salted SHA-256 ranking (`munim/holdout.py`) | Reproducible, and the agent can neither pick nor predict the split, so it can't hold back the customers least likely to return |
| How many agents | Several cooperating agents (planner, critic, executor); one proposer plus a deterministic workflow | One proposer (any LLM or Pi agent) plus ordinary modules | Extra agents add failure modes without adding evidence, so the product avoids multi-agent theatre. The "critic" is the rule engine |
| Model output | Free text; tool calls that act directly; strict JSON parsed into a typed proposal | Strict JSON into `CampaignProposal`; malformed output is refused, never repaired (`munim/llm.py`) | Model output must never trigger an action by itself; it becomes a proposal that still passes every rule |
| Questions over sales data | Text-to-SQL; retrieval over records; fixed analytics functions | Fixed functions (`munim/insights.py`) | Text-to-SQL can return wrong numbers that sound right, which is the exact failure Munim exists to prevent |
| Calling the offer rails | Fire and retry on failure; idempotency key plus quarantine | Campaign id as idempotency key; an unknown result is quarantined with the budget held until a human confirms (`munim/engine.py`) | A blind retry after a timeout can pay twice |
| Authority to spend | Shared API key; per-request checks; signed single-use passports | HMAC passport bound to the offer, its exact customer list and the rules version, expiring in an hour (`munim/passport.py`) | The execution side can verify a spend on its own, and a stolen or replayed passport is useless |
| Audit trail | Plain logs; database rows; hash chain | SHA-256 hash chain (`munim/ledger.py`) | Edits, deletions and reordering are detectable. Limitation: an attacker who controls the whole store could rebuild the chain; publishing or signing the head hash would close that, and is not built yet |
| Storage | Database now; in memory | In memory | The prototype runs as one process; production would keep the same append-only ledger in a database |
| Browser demo | Call the Python API from the page; re-implement the rules in JavaScript | Mirror the rules in `docs/rules.js` and test parity on 1,500 random cases | The demo needs no server and works offline, and parity tests stop the two copies drifting apart |
| Deployment | A cloud backend; static hosting | GitHub Pages for the demo; the API runs locally with one command | Nothing in the pitch needs a live backend; fewer moving parts on demo day |
