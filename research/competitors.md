# Competitors, substitutes, and spend controls for AI agents

Independent research pass by a separate reviewer. All sources checked **23 Oct 2026**. Covers competitors and substitutes for Indian small merchants (Part B) and spend controls for AI agents (Part C).

**How to read this file**
- Quoted text is an exact string from a page I opened. Web pages were read through WebFetch, whose quotes are exact but short. GitHub repos were read from raw files or a shallow clone.
- Confidence: **High** = primary source, opened, unambiguous. **Medium** = press, or primary but ambiguous. **Low** = inference.
- Each section lists what I did *not* verify. No capability appears here unless a source I opened supports it.

### Part B: inferences
- **Inference:** Indian SMB retention tools (Reelo, m'Loyal) cover capture, segment, message and reward, and report "attributable" revenue or ROI. None I opened claims holdout-based incrementality, a margin floor, or a spending limit on campaign rewards.
- **Inference:** Payment apps (PhonePe, Google Pay) compete on acceptance, alerts, loans and platform-funded rewards. In their public listings they do not offer merchant-run retention campaigns.

### Part C: synthesis

**Verified across the sources opened.** Every control falls into one of these categories:

| Control type | Where it appears |
|---|---|
| Per-transaction amount ceilings | ACP `max_amount`, AP2 Amount Range |
| Total budgets | AP2 Budget |
| Frequency or recurrence | AP2 Agent Recurrence |
| Payee or merchant allowlists | AP2 Allowed Payee, ACP `merchant_id` |
| Expiry or date windows | ACP `expires_at`, AP2 Execution Date, Reserve Pay 90 days (reported) |
| Agent identity and registration | Mastercard, Grantex in P3P |
| Revocation | Razorpay pilot, P3P |
| Audit trails | NPCI (reported), Grantex |
| Tool allowlists and read-only modes | PayPal `actions`, Razorpay `READ_ONLY` |
| Human approval of a suggested spend | Paytm Pi |

**Answer:** none of the sources I opened describes authorisation of merchant-side marketing spend that checks the spend against the merchant's margin, discounts customers who would have returned anyway, or requires a holdout before approving or continuing. Confidence is **medium**: this covers only the public documents I read, and absence on those pages is not proof of absence. Paytm's own Pi job listing names "incremental revenue" and "guardrails" as goals, so Paytm could build this itself.

**Inference (defensible framing for Munim):** existing agent-payment standards answer "may this agent pay this much, to this payee, now?" for a buyer. Munim answers "should this merchant pay this cashback at all, given margin and what customers would have done anyway, and did it work?" The two layers complement each other. Munim's output (an allow, gate or deny decision plus a signed single-use passport) could feed a mandate-style rail such as AP2-type constraints or UPI Reserve Pay. It does not replace them.
